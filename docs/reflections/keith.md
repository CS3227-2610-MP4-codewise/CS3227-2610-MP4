# Reflections on developing Codewise — Keith

Developing the student side of Codewise made me more deliberate about what I asked agents to do and how I judged their work. I used agents for planning, implementation, alternative interface designs and review, while also building a tracker to understand their resource use. The main lesson was that more activity did not necessarily mean more progress. I needed a way to connect each assignment to a useful result, and to distinguish what the records actually showed from what I hoped the workflow would achieve.

## 1. Multi-Agent SE worked best when each agent had a clear boundary

The student-drafts work gave me the clearest example of a coordinated workflow. A coordinator managed the requirements and integration, a domain implementer built the submission behavior, and a reviewer inspected the result. Once the domain work was reviewed, three UI implementers built alternative workbooks using CodeMirror, a textarea with Prism, and Monaco. Each worked in a separate worktree from the same domain commit. This let me compare concrete implementations without having three agents overwrite the same interface. 

That separation required more preparation than simply asking several agents to build the feature. They needed the same requirements and design reference, a known starting revision, permitted files and an explicit description of what they should return. Shared contracts, server code and migrations were outside the UI variants' scope. The coordinator still had to check that restriction and rerun verification. I would use this coordinator, bounded implementer and reviewer pattern again, but decide the boundaries before launching the agents.

The reviews showed why coordination could be useful. The domain review raised two medium and eight low findings, followed by another low finding after repair. The UI reviewer found that Monaco conflicted with the Worker's content security policy, even though its automated checks passed. That was a high finding left open in the comparison. I eventually chose the textarea and Prism variant for its overall appearance and because it added no dependency. The useful result was a better informed choice about the actual application, rather than three successful test reports. 

I returned to this approach when revisiting the question views. By then, students could submit work and read released feedback, but the submitted answers and feedback were on an all-question attempt page reached through a separate tab. I wanted the relationship between the question, the student's submitted answer and the instructor's feedback to be clearer. The revised layout placed three views beside the current question: Working copy, Submitted attempt and Released feedback. This gave the redesign a concrete purpose: students should be able to inspect their work and feedback for the same question without repeatedly moving between the workbook and a separate attempt page. 

For this change, I asked the coordinator to use multiple agents to generate drafts of the improved UI. Three read-only planning agents received identical prompts and proposed their approaches independently, without seeing one another's output. Three implementation agents then turned those proposals into working alternatives in separate Git worktrees. They worked within the existing student UI and design system, so the comparison concerned how to organize the interaction and scope the change. The proposals exposed choices that were easy to overlook in a visual sketch, such as whether Previous/Next followed the submitted attempt's question version, whether the selected feedback version survived a question change, and what happened at the end of a historical attempt. 

I chose alternative A, and the coordinator applied it with further fixes before completing the remaining tasks. The resulting interface kept the selected attempt across question navigation, scoped feedback to the current question and retained the all-question page as an attempt summary. Submission times also replaced potentially misleading attempt numbers, which could change as older history pages loaded. These details mattered because a clearer interface needed to preserve which attempt and version the student was inspecting. The chosen draft was still a starting point: the coordinator added fixes for feedback markers, release-version selection and announcements, and later completed URL restoration and the overview entry point. 

This experience broadened how I thought about multi-agent work. It was useful for revisiting an implemented feature and comparing ways to make it easier to understand, as well as for dividing new implementation. Having several drafts made the interaction tradeoffs concrete enough for me to choose, while the coordinator remained responsible for reconciling that choice with the full requirements. However, the alternatives were not a user study, and selecting one did not establish that students would find it clearer. I would use the drafts to support a design decision, then check the selected flow with users rather than treating agreement between agents as usability evidence. 

To verify that the coordination pattern was followed, I needed more than role descriptions in a workflow document. Triggering meant checking that the expected implementation or review assignment actually occurred. Context management meant checking the brief and starting revision. Resource sharing meant checking the worktrees and changed files against the permitted scope. Handoffs meant checking returned revisions, findings, repairs and exact verification results before integration. The tracker recorded parent-child links and spawning turns, but some records lacked terminal evidence. Those gaps meant I could describe observed assignments without claiming complete coverage of every agent's activity.

There were also unavoidable dependencies. The UI agents started after the domain baseline was ready, and merging depended on review and my choice. Monaco's CSP issue required a shared infrastructure decision that another UI agent could not authorize. In released feedback, composition and producer changes needed Darryl's review because he owned the assessment and identity boundaries. These were genuine blockers, but I did not collect a sufficiently complete agent-state timeline to say how long agents were idle or whether the coordinator was overloaded. A long gap between recorded turns would not establish either conclusion. Next time, I would record blocked and resumed times alongside the dependency and next owner. 

I also learned to resolve disagreements against requirements and evidence. During the editor work, the design wording was revised following the reviewer's interpretation of editable older versions and one-based URLs. In the later released-feedback UI review, a focus-only heading was flagged under the brief's literal target-size rule. After inspecting the finding, I recorded it as not applicable and accepted the UI following my manual pass. These cases required different responses. A reviewer could reveal an ambiguity worth fixing, but its finding still needed interpretation rather than automatic acceptance.

The costs were substantial. All three editor variants implemented a complete workbook, each received review and a repair round, and only one was merged. This bought a realistic comparison, but duplicated implementation and verification. The UI-variants checkpoint reported 113,120,713 cumulative tokens across the increment, with partial coverage; that figure also included earlier planning and domain work. It cannot be treated as the isolated cost of the three variants or proof that delegation was inefficient. It does show why I should budget for the entire comparison, including work I will discard.

For me, the benefits justified using agents to explore a consequential editor choice, compare clearer question-view interactions and review substantive changes. The records do not establish that this was faster or cheaper than one capable agent. For another project, I would first compare smaller prototypes and build several complete alternatives only when the decision depended on realistic interaction. Independent review is valuable when a defect could cross an authorization, persistence or accessibility boundary. Routine questions, small corrections and tightly sequential tooling work generally belong with one agent; the turn-activity tracker itself was implemented without children for that reason. [5]

## 2. Context Engineering meant making the current decision easy to find

My student features depended on services owned by Darryl, so context had to explain both the desired behavior and the limits of my authority. Repository instructions established ownership, one authoritative store and security constraints. OpenSpec supplied the feature requirements and tasks, while ownership records and integration contracts described the shared changes that had actually been agreed. A role name alone could not give an agent permission to edit another owner's service.

I would keep the system-level instructions focused on durable rules, then use skills for bounded procedures such as proposing a change, applying tasks or recording an experiment checkpoint. The project-experiment skill was particularly useful as a statement of boundaries: recording required explicit opt-in, unavailable counters stayed unavailable, and logs preserved redacted results rather than raw prompts or internal reasoning. However, having a skill or installing hooks did not prove that the live client followed the complete lifecycle. The tracker records repeatedly distinguished synthetic verification from pending live callback checks. 

For an assignment, I would supply the goal, requirement IDs, accepted decisions, source revision, owned files and completion criteria upfront. Those facts determine whether the agent starts the right work. Detailed implementation files, historical discussions and older evidence can be retrieved as needed. The editor variants benefited from sharing the same domain baseline and workbook requirements; each agent did not need to reconstruct every earlier product discussion before building its alternative.

The organization mattered as much as the quantity. A current decision buried among old proposals is harder to apply than a short current-state summary with links to its history. One integration review had to distinguish an earlier proposed submission fingerprint and key scope from the later accepted contract. Keeping both documents was useful for provenance, but leaving their status ambiguous could have caused unnecessary changes to Keith-owned submission behavior. I would mark superseded proposals explicitly and put the authoritative decision near the point where an agent begins work.

This was also the clearest warning about adding more context. More history can give an agent more conflicting instructions to reconcile, especially when a proposal resembles an accepted decision. Signals I would watch for are repeated questions about settled choices, attempts to reopen agreed contracts, and rereading the same files without a new conclusion. The repository showed a real ambiguity that required reconciliation; I did not run a controlled experiment proving that longer context caused poorer performance. The lesson is to curate status and relevance before increasing the amount supplied.

For `notes.md` or a handoff, I would preserve the objective, exact revision, owned files, accepted decisions and their reasons, remaining tasks, failed approaches and the next action. Verification needs exact commands and outcomes, including skipped tests and the limits of mocks. A synthetic route test, a real local D1 check and my reported manual acceptance answer different questions. A useful continuation should also identify who owns each blocker and which shared-file window is authorized. This would let another agent resume from reviewable conclusions without replaying the whole conversation. 

## 3. Resource-aware Use required measuring the work around implementation

I built the experiment tracker because a final answer gave me little visibility into the resources used to reach it. The tracker linked sessions and children, separated input, cached input, output and reasoning output, and later added per-turn activity and reconciliation tables. Explicit start, pause, resume and stop boundaries helped separate opted-in feature work from general questions. Earlier whole-session pilot totals were retained as legacy evidence and excluded from bounded comparisons. This improved the meaning of the measurements, even though missing terminal records and work performed outside a tracked run still limited coverage. 

Model allocation was one experiment within that workflow. The editor implementation used Sonnet 5.5 agents, with Opus 5.5 handling coordination and review; the recorded turns generally used medium effort. This was a practical way to assign bounded implementation separately from integration and judgment. It did not establish that either model was optimal, because their assignments differed. Next time, I would compare models on similar tasks and judge accepted results, repair effort and total consumption together. Mechanical formatting and checks should remain with deterministic tools, while additional reasoning effort should have a specific uncertainty to resolve. 

Caching made the input figures easier to misinterpret. At the student-drafts final-checks checkpoint, reported input was 149,544,265 tokens, including 146,019,157 cached input, approximately 97.64%. These were cumulative counters with partial coverage, not one prompt. Cached input was already part of input, so it could not be added again or described as tokens that had disappeared. I did not have a cache-disabled baseline and cannot state how much actual token usage was reduced. 

To reduce cache misses, I would keep durable instructions stable, avoid unnecessarily rewriting the shared task context, and retrieve changing details separately. To reduce repeated input more generally, I would use concise continuation notes and stop rereading broad files once the relevant decision was established. These are related but different goals: cache reuse can make repeated context less expensive to process, while avoiding an unnecessary call removes work altogether. My measurements showed substantial cache reuse; they did not isolate the saving caused by any one context strategy.

The reasoning counters allowed a narrower calculation. One finalized student-drafts proposal turn reported 25,235 output tokens, including 3,596 reasoning output tokens, approximately 14.25% of that turn's output. This is not 14.25% of all tokens used for the task: the per-turn table did not supply the corresponding input denominator. It also cannot represent the entire proposal, which involved several turns. Persisting decisions, evidence and rejected approaches could help a continuation avoid repeating investigation, but I would preserve those useful conclusions rather than raw internal reasoning. I did not measure a saving from doing so. 

Rework also consumed resources outside the code itself. In released feedback, the first read-count instrumentation reported zeros and had to be replaced with a Proxy before the measurement was meaningful. A later student-progress probe used a mis-scoped Vitest root, hung and was stopped before a different approach was used. These are concrete examples of tool work that needed correction. They do not justify labeling every retry wasteful: rerunning a check after a repair can establish something new. I would ask whether the next call tests a changed hypothesis, rather than repeating it because the previous result was inconvenient. 

The heaviest recorded increments included complete alternative implementations, broad browser review, repeated verification and review-repair cycles. Student drafts reached 150,452,362 reported cumulative tokens at its final-checks checkpoint, with partial coverage. Student question views also involved three proposals and three worktree implementations before one was selected. These records make alternative-building an obvious candidate for tighter scope, but the increments differ too much to rank all task types fairly or claim a measured reduction from later work. [1; 8]

My next step would be to set a resource budget and a stopping condition before each comparison, record the reason for retries, and measure cost per accepted result. I would retain enough budget for review and repair instead of spending everything on the first implementation. The tracker helped me see where measurements were missing and where coordination generated extra work. The responsibility remained mine to decide whether that extra work answered a useful question.
