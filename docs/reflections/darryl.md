# Reflections on developing Codewise — Darryl

Looking back at Codewise, the biggest change was in how I judged AI-assisted work. In MP3, I had already found that adding agents could create more coordination than progress. MP4 gave me a chance to examine that lesson more carefully while building shared authentication, course authorization and instructor assessment features. I became more concerned with whether an agent's contribution could be checked, whether its context supported its decisions, and whether the resources spent produced a useful result. Three experiences, in particular, changed how I would approach another project.

## 1. Multi-Agent SE was most useful when another agent challenged something specific

The secure AI gateway was a reasonable place to use several agents because its work could be separated. One specialist handled the provider transport and synthetic tests, another handled D1 storage and admission controls, and the main agent integrated their interfaces. A separate reviewer inspected the security boundaries. These were actual delegated assignments, rather than files describing an ideal team. However, the coordinator still needed to understand the complete flow, particularly how authorization, retries and quota accounting interacted. Splitting implementation did not remove that responsibility. [1]

A later gateway audit gave me a concrete example of the value of review. The independent reviewer found that malformed provider content could cause valid usage information to be discarded before overage accounting. Rejecting an unusable answer was appropriate, but forgetting the resources consumed by that answer was a separate defect. The main agent preserved validated usage through internal transport errors and added regression coverage. The reviewer then rechecked the repair. This contribution mattered because it changed the system's behavior on failed requests, rather than merely adding another approval to the workflow. [2]

The finding also exposed a weakness in how I had divided the problem. Transport validation and quota accounting looked like separable implementation tasks, but their failure paths crossed that boundary. A locally correct decision in one component could undermine a guarantee in another. This suggests that specialist implementation should be divided by clear ownership, while review should deliberately follow interactions across those divisions. Otherwise, I risk asking every agent to inspect its own component and leaving the most consequential assumptions between components unexamined.

The coordination pattern I settled on was a main agent that both implemented and integrated, optional specialists for separate work, and a read-only reviewer for substantive behavior changes. The workflow skill specified when review should be triggered, what a delegation brief must contain, and when repairs should return for focused re-review. Shared contracts and migrations had one writer at a time; separate role names did not authorize concurrent edits to the same file. To check whether this pattern actually happened, I needed to compare the recorded spawn/reuse events, assignments, permitted files, returned checks and repair history. A completed checklist alone could not verify triggering, context transfer, resource sharing or handoffs. The gateway records show this pattern in particular increments; they do not establish perfect compliance across every project turn. [1; 6]

Parallel implementation also had a sequential dependency: integration depended on the specialists' interfaces, and final review depended on having a candidate to inspect. The main agent remained the point where findings, repairs and verification accumulated. That made it a potential bottleneck, but I did not record agent-state timelines sufficient to quantify idle time or prove overload. Provider verification and local test-environment failures also blocked progress at recorded checkpoints; launching another agent could not remove those dependencies. I would record start, ready, blocked and resumed times next time, distinguishing useful concurrent work from agents merely remaining available. [1; 2]

I also tried a small coordination exercise around source-range validation. The main-only exercise identified reversed ranges and coercible fractional indices. A worker in the coordinated exercise identified those issues and numeric-string coercion; a reviewer reproduced selected cases and raised surrounding identity and line-splitting concerns. Initially, this looked like evidence that more agents found more problems. On closer inspection, that conclusion was too strong. Both exercises involved the same defect class, and the reviewer had already seen the worker's findings. There was no blinded comparison, comparable end-to-end timing or attributable experiment-level token total. The worker's reported six seconds excluded startup and communication, so it could not fairly be compared with the main agent's work. [3]

This distinction changed how I interpreted “independent review.” A separate agent can usefully verify a repair while knowing the original finding, but that does not make its finding an independent discovery. An additional agent can also inherit the author's framing and repeat the same blind spot. In this case, verification was useful; the experiment simply did not establish how much fresh discovery came from the extra participant.

Disagreements needed evidence rather than a vote between agents. In the synthetic evaluation review, a suspected escaping error was checked and retracted without a code repair. Other findings about misleading experimental claims were accepted and led to corrections. This was a useful distinction: the main agent should require a requirement, reproducible example or source-level explanation before changing behavior. A review that retracts an unsupported claim can improve the result just as accepting a supported finding can. [3]

My conclusion is therefore narrower than saying multi-agent development was faster or cheaper. It produced useful defects and corrections, especially at security and accounting boundaries, but my experiments do not establish a productivity improvement. Next time, I would keep one agent responsible for a bounded feature and add specialists where there is a clear implementation boundary or a specific reason to seek another perspective. For a comparison, I would use different but comparable tasks, vary their order, give the reviewer the source and requirements before the author's findings, and include integration and repair work in the resource measurement.

For a small correction, a routine question or tightly sequential work requiring the same context throughout, I would keep the work with the main agent. For a security-sensitive boundary or genuinely separate subsystem, the observed review findings justify considering another agent. The benefit outweighed the cost in the practical sense that specific defects were found and repaired; whether the overall arrangement used fewer resources than a capable single agent remains unanswered.

## 2. Context Engineering meant controlling the basis of a decision, then testing what that context actually changed

For instructor assessment, giving the model the whole project would have been an easy starting point. It would also have mixed relevant evidence with material that should not influence the current assessment. The useful context was the selected question, rubric, submitted source and explicitly selected reference, tied to the versions being assessed. Student code and comments needed to remain evidence to inspect, rather than instructions granting the model authority. This made context selection a correctness and privacy decision as well as a prompt-size decision. [4]

My first context experiment showed how easily I could overstate the benefit. A locally constructed full-context JSON artifact contained 2,474 bytes, while the selected artifact contained 1,033 bytes, approximately 58% less. Both conditions accepted the valid and untrusted-output-flag variants and rejected fabricated excerpts, missing criteria and out-of-range scores. However, both conditions called the same deterministic validator with the same publication and attempt. The extra full-context material was never consumed. The experiment established a smaller serialized artifact and a validator control; it did not establish better model answers, lower model latency or token savings. The five variants were also variations of one synthetic attempt, not five independent submissions. [3]

The deeper problem was that my measurement did not exercise the mechanism behind my claim. If I wanted to know whether selected context improved reasoning, a component whose behavior did not depend on the extra context could not answer that question. Passing the control was useful for checking the harness, but it should have led to a model comparison using fixed cases and reviewed answers. I learned to ask what must actually change between conditions before interpreting a difference in artifact size as an improvement in the product.

The later live evaluation was more revealing. I used six synthetic versions of a Python `positive_sum` task: correct, partially correct, plausible but incorrect, blank, an alternative correct implementation and a source comment containing an injection instruction. Proposed rubric expectations were fixed before the calls. For example, `return sum(values)` should lose the criterion requiring zero when there are no positive values, because a negative-only list returns a negative sum. No submitted code was executed; the evaluation used static reasoning. [4]

The model sometimes recognized the problem in its explanation but still assigned the wrong score. Under prompt v3, the partial solution received C2=3 even though its explanation said the criterion should score zero. The application accepted and stored that candidate. A blank submission also received full marks while its explanations said minimum scores should apply. These results exposed the limits of structural validation: valid JSON, permitted score ranges and genuine source excerpts do not establish that a grade follows from the rubric.

This was more concerning than a simple factual error because parts of the answer appeared to support one another. A plausible explanation and accurate quotation could make the numerical score seem trustworthy, even when they contradicted it. The interface could therefore present several individually credible-looking fields without presenting a coherent assessment. Instructor review remained necessary, but asking an instructor to review should not become a reason to accept avoidable contradictions without warning.

The repairs also needed to be distinguished. Accepting one complete JSON code fence fixed a formatting failure while retaining ordinary validation; it did not fix the incorrect judgment inside the response. General boundary-case instructions in v3 still left contradictory scores. A later v4 prompt added consistency and reference non-disclosure instructions, and the final targeted partial-solution check returned the proposed 0/0/3 score with accurate line-two excerpts. That was a useful repair result, but one successful rerun did not demonstrate reliability. Repeatedly repairing and retesting the same example also risks optimizing the prompt for the examples I already know. A separate set of unseen cases would be needed to assess whether the improvement generalized. [4]

The blank-source safeguard offered a different kind of improvement: it blocked AI dispatch for empty or whitespace-only source and preserved manual assessment. This moved an unambiguous admission decision into application code. Its offline checks did not establish protection for comments-only or other incomplete programs, but the supported claim was clearer than “the model has been told to be careful.”

The injection case gave another reason to avoid broad claims. Neither inspected response followed the comment's instruction to award full marks or reveal the private reference. However, both quoted the wrong line range and were rejected, and their raw scores differed. Those observations describe those particular outputs; they do not establish general resistance to injection. Likewise, rejecting a draft for inaccurate evidence prevented its release through that path, but did not show that the model understood the security boundary. [4]

I now see context engineering as including evidence selection, instruction boundaries, versioning and output interpretation. Changing the trusted prompt changed its fingerprint, which could make older candidates stale on read or adoption. A prompt improvement therefore had application compatibility consequences too. Next time, I would plan prompt-version recovery alongside the prompt itself and separate checks for formatting, evidence accuracy, scoring consistency and instructor usefulness. A single “valid output” result hides too many different questions.

The development agents needed deliberate context organization too. I used repository instructions for durable constraints such as ownership, one authoritative identity store and no execution of student code, with a bounded workflow skill for coordination and verification. A task brief should supply the immediate objective, requirement IDs, source revision, file ownership and security constraints upfront. Detailed implementation files and older evidence can then be retrieved when needed. This avoids making an agent rediscover its permissions while also avoiding a full project history in every assignment. The local skill expresses this approach, although I did not run a controlled comparison proving that its organization improved instruction following. [6]

The repository itself showed a reason to distinguish stable instructions from dated status. Its OpenSpec configuration retained earlier pending ownership and integration statements alongside later records that superseded them. More historical context could therefore create ambiguity about which decision was current. That is an observable maintenance problem, not proof that a longer prompt degraded model performance. Next time, I would keep current decisions concise, mark superseded decisions clearly and link the history separately. For a handoff or `notes.md`, I would preserve the objective, exact revision, owned files, accepted decisions and reasons, failed approaches, exact checks and results, unresolved findings, remaining budget and next action. That would let the next agent recover the state without replaying the entire conversation. It should also distinguish a mock result from a live result and a proposed policy from actual authorization. [2; 7]

## 3. Resource-aware Use meant budgeting for useful outcomes, including failures and rework

The first live assessment attempt returned HTTP 200 but reached its 512-token output cap midway through an annotation. It consumed 489 input and 512 output tokens without producing a valid candidate. A low output limit had bounded consumption, but it had also prevented the required response from completing. Increasing the cap to 1,024 and revising the prompt produced a valid correct-solution candidate using 490 input and 821 output tokens. This showed why choosing the smallest cap is not automatically efficient: an unusable answer still consumes resources and creates repair work. Because the prompt also changed, the improvement cannot be attributed to the cap alone. [4]

I bounded the evaluation at 12 provider attempts, including repeats and targeted repair checks. The harness disabled automatic retries, recorded dispatch and stopped on failure or uncertainty. Independent review found gaps in concurrency, cancellation and continuation accounting, which required repairs before proceeding. After the first failure, restarting with a fresh local database would have lost the local accounting history. Continuation instead retained the original ledger and conservatively reconstructed quota charges; the records explicitly state that this did not recover the lost original request identity. [4; 5]

This made the experimental setup part of the resource problem. A request ceiling is only meaningful if retries, restarts and uncertain work cannot silently escape it. Spending development effort on the ledger was therefore justified by preserving the experiment's bound and provenance. However, that preparation also consumed time and development-agent resources. I cannot claim the evaluation was efficient merely because its final provider-token total was small.

All 12 attempts were eventually used, with reported provider consumption of 6,123 input plus 7,860 output tokens, or 13,983 in total. The revised conservative reservation ceiling was 208,384 tokens. These figures serve different purposes: the reservation was an admission bound, while reported usage described the completed calls. The difference was not a measured saving against a baseline. Some calls failed validation, and others produced materially wrong accepted scores. Once the budget was exhausted, I stopped rather than continuing until every example looked successful. Q3 and Q6 therefore retained unresolved findings, and the evaluation recommendation remained “needs repair.” [4]

Stopping also affected the honesty of the result. If I kept rerunning a failing example until one answer looked correct and reported only that answer, I would spend more resources while making the evidence less representative. The fixed ceiling forced a decision about which repair was worth checking and left the unresolved cases visible. It did not establish a statistically reliable failure rate: the 12 calls included different prompt versions, repairs and repeats, rather than 12 independent trials under one fixed condition.

I also needed to distinguish resources used to develop Codewise from resources used by its assessment model. My development recorder reported input, cached input, output and linked child activity, but several prompt-level measurements were unavailable or provisional. Cached input was already included in input, and shared-turn totals could not honestly be divided among individual prompts. Consequently, those logs could document substantial development activity without supporting a percentage saving from delegation. The provider's 13,983-token evaluation total was a separate measurement and could not stand in for the cost of building and reviewing the feature. [1; 3; 5]

The recorder did make repeated context processing visible. One interrupted quality-evaluation main-agent record reported 53,263,094 input tokens, including 53,198,592 cached input, and 58,276 output tokens. Approximately 99.88% of its reported input was cached. This was accumulated usage across responses, not one enormous prompt. It showed extensive cache reuse alongside substantial repeated context processing; it did not show that I had reduced total tokens by 99.88%. There was no cache-disabled baseline or priced comparison. Keeping a stable instruction prefix, retrieving only relevant files and preserving concise continuation notes are approaches I would test to reduce cache misses and repeated reading, but my records do not isolate their benefit. Nor does a high cache fraction make unnecessary calls free of latency or coordination cost. [5]

That same checkpoint linked eight completed reviewer records, totaling 6,606,320 tokens, alongside the main agent's 53,321,370 total. It gives a concrete example of a repair-and-review sequence consuming substantial development resources. It does not prove that review was wasteful: the reviewer found accounting and harness defects that affected whether the experiment could be trusted. Equally, I cannot rank all task types from incomplete project coverage or claim that later smaller turns demonstrate a reduction on comparable work. Repeated analysis, continuation rehearsals and broad verification deserve measurement because their costs accumulate around implementation. Provider retries were explicitly disabled for this evaluation, while repair reruns were separately counted; those are different sources of repetition. [4; 5]

Model choice needed the same discipline. The live assessment used `qwen3-coder-next`, with an output budget adjusted to fit the structured task, but I did not compare it with another model. A coding-oriented model and a large context window did not guarantee accurate grading. Development-agent model identity was unavailable in several logs, so I cannot reconstruct a reliable model-by-task efficiency comparison. For future work I would use deterministic tools for formatting and mechanical checks, then compare candidate models on the same rubric cases and constraints before assigning judgment-heavy work. The relevant criterion would be reliable accepted outcomes including repair cost, rather than model size alone. [1; 4]

I also do not have a defensible percentage of tokens spent on internal reasoning for a specific task. Output totals cannot supply that percentage without a separately attributable reasoning-token measurement. Persisting a concise account of decisions, evidence and rejected approaches could help another agent avoid repeating investigation, but that is a proposed benefit, not a measured result here. I would preserve those reviewable conclusions in handoffs rather than assume a transcript of internal reasoning was necessary for continuity.

For another project, I would define success criteria and stop conditions before dispatch, reserve some budget for repairs, and measure cost per useful validated result alongside defect severity and rework. I would also separate controlled comparisons from exploratory debugging: changing prompts and caps during this evaluation helped repair the feature, but weakened any claim about which individual change caused improvement. My role became deciding which uncertainty was worth spending the next request on, and what evidence would justify trusting the result. Keeping those decisions and failures visible gave me a more defensible basis for the next iteration than reporting only the final successful response.
