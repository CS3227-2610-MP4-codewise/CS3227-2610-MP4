## KCOU1 — explicit creator eligibility

Implemented additive migration0009 creating `course_creator_capabilities(user_id PRIMARY KEY REFERENCES auth_accounts(id), active INTEGER CHECK(active IN (0,1)), granted_at INTEGER NOT NULL)`. It seeds only from the completed singleton owner record joined by account_id, issuer, subject and email to the same active auth account and existing auth_administrators row. No email-literal lookup, fallback admin grant or fixture insertion. It does not modify0006/0007, owner credential pins, bootstrap completion, account IDs or prior memberships. Migration continuity is tested against isolated real local D1.

For an already completed owner the migration adds only this capability row. For an environment whose bootstrap completes later, read-only discovery also recognizes a **reconcilable owner**: the exact current completed-owner/account/admin/provider-pin checks pass and no capability row exists. Discovery returns canCreate:true for that state without writing. POST inserts the missing capability inside its guarded batch using the same completed-owner join, before enforcing the active-capability guard and course writes. An existing inactive row is a revocation tombstone: discovery returns false unless the independent current-instructor branch passes, and reconciliation never updates/reactivates it. Test both migration-before-bootstrap and bootstrap-before-migration orderings. This handles install-before-bootstrap without reopening bootstrap or needing removed operator passwords. Capability revocation persists across restarts/deploys. Migration application never calls Firebase or copies local data.

Runtime creator predicate requires a current SH-AUTH session and active account, then either: (a) explicit active creator capability plus current completed owner identity match and auth administrator row; or (b) at least one active instructor membership in an active course. Capability alone on an unrelated account is insufficient. Generic admin, matching email, browser flags and student membership alone are insufficient. First-admin provider pin validity still comes from existing ManagedAuthRoutes; final D1 guard joins account/session/provider binding to owner pins. Recheck account/session/admin/capability and instructor-course currentness within the committing batch, including no-work replay. No entitlement grants unrelated-course read/write access. Removing the last instructor membership removes creator eligibility unless the current first-admin branch independently passes.

## KCOU2 — additive command and discovery

Implemented strict public shapes in `src/shared/courses.ts`, using the existing closed parser and safe error boundary:

| Endpoint                    | Request                                   | Response                                                                                                                                          |
| --------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/api/courses/creation` | No body; current session                  | 200 `{canCreate:boolean}`; no source course, admin basis, provider identity or private data. This is presentation discovery, never authorization. |
| POST `/api/courses`         | Exactly `{name:string,requestKey:string}` | 201 first commit or200 matching replay: `{course:{id:string,name:string}}`. No role/admin/session expansion.                                      |

Name: valid Unicode, trim outer whitespace once;1–120 Unicode code points, at most480 UTF-8 bytes, no C0/C1 controls, no blank-only value. Reject invalid input before writes; no silent truncation or Unicode normalization. Keep normalized displayed name and fingerprint identical. Course names are not globally unique. requestKey: UUID generated per logical user submit; strict canonical UUID syntax, max36 ASCII bytes. Unknown fields including userId, creatorId, role or administrator are rejected. Bounded streamed JSON body at2KiB; Content-Type application/json required. Session/origin/CSRF guards run before mutation; no route GET mutates capability/creates a course.

Use current same-origin cookie/session and X-CSRF-Token; do not accept identity in the body. Responses and failures use no-store and existing security headers. Safe errors:400 INVALID_CONTRACT;401 UNAUTHENTICATED;403 FORBIDDEN;409 IDEMPOTENCY_CONFLICT for changed payload or revoked/inactive prior result;429 RATE_LIMITED with bounded Retry-After;503 UPSTREAM_UNAVAILABLE for uncertain storage/provider availability. No SQL/provider error, credential, capability secret or foreign-course detail in a response. Proposed new-create rate limit:10 attempts/minute per admitted account using existing shared D1 rate limiter; replay remains guarded and may be rate limited. Limits do not replace idempotency.

Synthetic success request: `{"name":"Programming studio","requestKey":"a368170d-b3aa-4af4-83f5-8cd624037a3a"}`. Response: `{"course":{"id":"course_synthetic_1","name":"Programming studio"}}`. A student-only discovery returns `{"canCreate":false}` and POST403; an authenticated empty pinned owner returns true with the same empty GET `/api/courses` list as before creating.

## KCOU3 — atomic writes and retry/currentness

Implemented additive receipt table: `course_creation_receipts(user_id REFERENCES auth_accounts(id), request_key TEXT, name TEXT, course_id UNIQUE REFERENCES courses(id), created_at INTEGER, PRIMARY KEY(user_id,request_key))`, with required fields. The canonical name is the fingerprint for this single-field command. Key scope is stable admitted account, operation and environment/database; never cookie session or email. Receipts do not expire in this increment: deletion could let an uncertain retry create a second course.

One same-D1 batch checks current session and creator authority with an aborting guard, verifies an existing receipt has the same canonical name and its course and creator membership remain active, inserts the course only if no receipt exists, inserts its creator instructor membership, and persists the receipt. Generate the candidate course ID server-side; on concurrent retries every conditional statement must resolve the winning receipt/candidate consistently. Do not rely on an unlocked SELECT, changes() from unrelated statements, SELECT-then-insert in separate calls, or ON CONFLICT that rewrites an existing course/membership. Forced failure at any of the three writes must roll back all three. After commit read the receipt through current authorized scope; if authority has changed, fail closed without treating that as proof the transaction rolled back.

Two simultaneous same-account/same-key/same-name requests yield one course/membership/receipt and the same ID. Same key/changed canonical name yields409 without writes. Different accounts may use the same key independently. A revoked receipt-result membership/course is not resurrected by replay even if the actor has instructor authority elsewhere. Receipt lookups are never access grants. Session/account/capability/admin/last-teaching-course revocation immediately before the guard denies the whole batch. Provider state cannot be atomically transacted with D1; use the existing current-provider check before the final local guard and document that external revocation detection is bounded by provider observation, not a fictional distributed transaction.

UI retains the same name/key after uncertain transport/503; Retry resubmits that pair. A changed name after uncertainty must first resolve the original operation using its retained pair; do not silently issue a fresh key and imply the original failed. Disable duplicate submit/cancel while pending. Cancel before submission closes without writes. Display success/open only after a valid matching server acknowledgement; an uncertain result states that creation could not be confirmed. Reauthorize opening through current course authority. Do not store credentials/CSRF tokens in localStorage. Form draft/retry state can remain in mounted memory; refresh recovery is explicitly unverified until implemented and tested.

## KCOU5 — registration, acceptance and revoked receipts (later increment)

Registered means admitted stable app account mapped to the Firebase project/UID, never prior invitation existence. New intended recipients choose a password with valid mailbox/provider proof; registered recipients submit existing password, including when already signed in. One combined password-and-join action commits the exact invited role; no GET/scanner/sign-in-without-invite grant, wrong-account acceptance or password replacement to repair membership. Preserve opposite-role rows. Provider success with D1 interruption recovers against the same UID/account and current proof generation.

Final acceptance batch rechecks intended recipient/session, active course, exact pending invite/generation/target role and current inviter instructor authority, then writes membership plus accepted receipt together. Same valid retry acknowledges existing access; accepted receipts cannot restore revoked memberships. No additional public signup, auth-admin invitation or implicit unrelated-course access. These are agreed product invariants with proposed transaction mechanics, not implemented course-acceptance contracts.
